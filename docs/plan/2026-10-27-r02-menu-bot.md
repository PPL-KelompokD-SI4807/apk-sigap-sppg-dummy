## Kondisi kode saat ini (hasil pembacaan)
- `TelegramUpdateHandler::callback()` hanya `answerCallbackQuery` (no-op). `allowed_updates` sudah memuat `callback_query`.
- `/start` dan `/bantuan` memakai satu tombol `web_app` "Buka SiGAP" (URL akar Mini App). Teks/foto/suara ke Agen AI sudah dijaga `punyaSesiPenuh` di handler dan diulang di `ProcessAiMessage`.
- Tombol notifikasi memakai `TelegramBotService::miniAppUrl($query, $hashPath)` -> `https://.../miniapp/?x=y#/<rute>`; investor membawa `?sppg=<id>` (petunjuk, divalidasi server). Mini App: `router.js` hanya membaca hash berawalan `#/`; `main.js` membaca `?sppg=` (investor), `?draft=` / `startapp=draft_`. Belum ada deep link rute generik lewat query/`start_param`.
- `TelegramBotService` belum punya `editMessageText` / `editMessageReplyMarkup`.
- `SppgAktif` (SPPG aktif investor) dihitung dari header `X-SPPG-Id` per request. Di job antrean tidak ada header: investor multi-SPPG = `BELUM_DIPILIH` (fail closed), `User::sppgAktifId()` null, `BaseSppgPolicy::sameSppg` menolak. Bot butuh jalur SPPG-eksplisit yang aman.
- `PersetujuanMenuService::putuskan($investor, $pengajuan, $keputusan, $catatan, $versiMenu)` dan `PersetujuanPengeluaranService::putuskan($investor, $pengeluaran, $keputusan, $catatan, $versi)` sudah memegang kunci baris, memeriksa pivot `investor_sppg` (`SppgAktif::milik`), dan melempar 409 terstruktur. Keduanya tidak bergantung pada header. Aturan catatan di Form Request (bukan service): tolak wajib `min:5`; menu `max:1000`, pengeluaran `max:500`; menu juga punya `perlu_revisi`.
- Hak keputusan: `Rbac::canDecide` / `config('rbac.keputusan')`: `persetujuan-menu` dan `keuangan` = investor; `pembelian-bahan` = akuntan (di luar lingkup bot R-02).

## Keputusan desain

### D1. callback_data: kode acak ber-HMAC + status di basis data (sekali pakai)
- Format: `b1.<kode>.<mac>`; `kode` = 8 byte acak base64url (11 karakter), `mac` = 6 byte pertama HMAC-SHA256 base64url (8 karakter) atas `kode|telegram_id` dengan kunci turunan `hash_hmac('sha256','bot-callback|v1', config('app.key'))`. Total sekitar 23 byte (batas Telegram 64).
- callback_data TIDAK berisi ID bisnis, versi, SPPG, atau aksi. Semua itu di baris tabel baru `bot_aksi` dan dibaca server. Alasan: ukuran, tidak ada yang bisa dipalsukan/diubah klien, dan sekali-pakai butuh status server.
- MAC memangkas tebakan/forgery tanpa menyentuh basis data (DoS ringan); verifikasi `hash_equals`. Kode palsu, kedaluwarsa, sudah dipakai, atau milik orang lain dijawab seragam ("Tombol sudah tidak berlaku. Ketik /menu.") agar tidak jadi oracle.
- Tabel `bot_aksi` (migrasi aditif baru, tidak mengubah/menghapus data): `id`, `kode` char(11) unik, `user_id`, `telegram_id`, `chat_id`, `sppg_id` null, `jenis` (`pilih_sppg`, `daftar_persetujuan`, `tinjau`, `setuju`, `tolak`), `subjek_tipe` null (`pengajuan_menu` | `pengeluaran`), `subjek_id` null, `subjek_versi` null (versi yang DILIHAT pengguna saat tombol dibuat), `status` (`aktif`, `dipakai`, `menunggu_catatan`, `selesai`, `kedaluwarsa`), `expires_at`, `used_at`, `catatan_expires_at`, `prompt_message_id`, `hasil`, timestamps. Indeks `(telegram_id,status)`, `expires_at`. Tanpa NIK/telepon/isi catatan.
- TTL: tombol 10 menit (`config('telegram.callback_ttl_menit')`); jendela balasan catatan 10 menit (`catatan_ttl_menit`). Dibuat ulang setiap layar dirender; menekan tombol lama tidak berbahaya.
- Sekali pakai atomik: `UPDATE bot_aksi SET status='dipakai', used_at=now WHERE id=? AND status='aktif' AND expires_at>now()`; harus 1 baris terpengaruh, sebelum memanggil service. Tekan ganda/replay update gagal pada UPDATE ini. Gagal 409 dari service tetap menghabiskan token (pengguna memuat ulang layar -> token baru, versi baru). Satu layar menerbitkan token terpisah per tombol; setelah satu dipakai, keyboard di pesan dihapus (`editMessageReplyMarkup`) dan token saudara di-set `kedaluwarsa`.
- Pengikatan: baris harus cocok dengan `callback_query.from.id` == `telegram_id`, `message.chat.id` == `chat_id` (hanya chat pribadi), dan `user_id` == pengguna yang ditemukan dari `telegram_id` saat ini. Pengguna dimuat ulang dari DB setiap callback (peran, aktif, sesi, bukan dari baris).
- Aksi tidak pernah dipercaya dari callback_data: sebelum melaksanakan, server menghitung ulang hak (D5).

### D2. Menu tombol per peran
- Perintah `/menu` (juga tombol setelah `/start` dan `/bantuan` untuk pengguna ber-sesi penuh) mengirim keyboard inline. Pintasan layar memakai tombol `web_app` (bukan callback), jadi tanpa kode/kedaluwarsa; ia hanya membuka URL yang tetap lolos login + Policy di Mini App.
- `BotMenuCatalog` (kelas baru, kode, bukan duplikasi RBAC): daftar butir `{id, label, modul_rbac, rute, predikat}`. Butir tampil bila `Rbac::can($user, modul, 'R') && ! Rbac::isSelfOnly($user, modul, 'R')` (atau `canDecide`/`aggregateOnlyModules` bila relevan). Aturan unit relawan ikut otomatis karena lewat `Rbac::letters`. `config/rbac.php` tetap satu-satunya sumber hak; perubahan matriks langsung memengaruhi menu. Tes konsistensi: tiap butir katalog menunjuk modul yang ada di `config('rbac.modules')`.
- Maksimal 6 butir + "Buka SiGAP", 2 per baris. Label Indonesia, tanpa data dinamis/pribadi.
- Tombol aksi dalam bot (callback) hanya untuk investor (D4).

### D3. Deep link per layar
- URL tombol: `miniAppUrl(['r' => '/rute', 'sppg' => id?], '/rute')`, yakni rute di query `?r=` DAN di hash `#/rute` (hash dipakai notifikasi yang ada; ketahanannya pada klien Telegram sungguhan belum terverifikasi, lihat risiko). `?r=` adalah fallback; Mini App memvalidasi `^/[a-z0-9/-]{1,80}$`, tanpa `//` atau `..`, dan hanya dipakai bila hash saat ini beranda.
- Rute yang ada dan dipakai (slug `registry.js`): `/jadwal`, `/log-produksi`, `/mutu`, `/bahan-baku`, `/bahan-baku/stok-menipis`, `/bahan-baku/kedaluwarsa-dekat`, `/pembelian-bahan`, `/menu-gizi`, `/persetujuan-menu`, `/persetujuan-menu/<id>`, `/keuangan`, `/keuangan/pengeluaran`, `/keuangan/pengeluaran/<id>`, `/keluhan`, `/rekap-harian`, `/notifikasi-perjalanan`, `/notifikasi-perjalanan/baru`, `/bukti-distribusi`, `/armada`, `/sppg`, `/titik-layanan`, `/pengguna`.
- Investor selalu membawa `sppg=<id>` (petunjuk; `parseSppgHint` + `setSppgAktif` sudah ada; server tetap memvalidasi pivot). Peran lain tanpa `sppg`.
- Login dulu tetap berlaku: Mini App membuka login, lalu `masukBeranda` -> `startRouter` mengikuti hash/`?r=` yang tetap ada di URL.

### D4. Tombol keputusan investor (menu dan pengeluaran) dan pemilihan SPPG
- Alur: `/menu` (investor) -> tombol "Menunggu keputusan" (callback `daftar_persetujuan`).
  - Investor 1 SPPG: lompat ke daftar. Investor >1 SPPG: layar pemilih SPPG (nama SPPG dari pivot `SppgAktif::milik`), tombol callback `pilih_sppg` yang membawa `sppg_id` di baris `bot_aksi` (bukan di callback_data). Tidak ada SPPG aktif tersimpan permanen; pilihan hidup di baris token dan diturunkan ke token berikutnya, serta SPPG selalu diverifikasi ulang terhadap pivot setiap tekan.
  - Daftar: maksimal 5 pengajuan menu `diajukan` + 5 pengeluaran `status_persetujuan=diajukan` untuk SPPG itu, hanya ringkasan (nama menu / kategori, nominal), tombol "Tinjau" (callback `tinjau`) per butir.
  - Layar tinjau: data segar dari server (sama dengan isi notifikasi; pengeluaran TANPA `uraian`; tanpa nota/lampiran), `subjek_versi` dikunci pada baris token, tombol [Setujui] [Tolak] [Buka di Mini App (web_app)]. Setujui satu ketukan dari layar tinjau (layar tinjau adalah konfirmasinya).
- Setujui: token `setuju` dipakai atomik; service dipanggil dengan versi dari baris token. 409 (versi/status berubah, sudah diputuskan) dibalas dengan pesan jelas + tombol "Muat ulang" (menerbitkan token baru). Pengajuan menu hanya `disetujui`/`ditolak` lewat bot; `perlu_revisi` hanya di Mini App.
- Tolak tanpa catatan: tidak boleh. Ketuk Tolak -> token menjadi `menunggu_catatan`; bot mengirim pesan `ForceReply` "Ketik alasan penolakan (min 5, maks 500/1000 karakter) sebagai BALASAN pesan ini, atau /batal", dan menyimpan `prompt_message_id`. Pesan teks berikutnya dari `telegram_id` itu yang (a) berupa balasan (`reply_to_message.message_id` == `prompt_message_id`), (b) dalam jendela waktu, (c) lolos sesi/RBAC ulang, dianggap catatan dan dikirim ke service (`ditolak`), TIDAK ke Agen AI. Teks lain tetap ke Agen AI seperti biasa. `/batal` atau token baru membatalkan. Satu `menunggu_catatan` per pengguna. Validasi panjang memakai aturan yang sama dengan Form Request (min 5, max menu 1000 / pengeluaran 500); gagal -> bot minta ulang tanpa menghabiskan jendela. Isi catatan tidak disimpan di `bot_aksi`; hanya di kolom keputusan resmi.

### D5. Verifikasi ulang di server (urutan WAJIB, sama untuk setiap callback/aksi)
1. Rate limiter per `telegram_id` (mis. 30 callback/menit) dan per chat untuk kegagalan.
2. Verifikasi MAC, muat baris, cek `status='aktif'`, `expires_at`, binding `from.id`/`chat.id`/`user_id`.
3. Muat pengguna dari DB: `canAuthenticate()`.
4. `SesiService::punyaSesiPenuh($user)`; jika tidak -> jawaban petunjuk login (tombol web_app ke akar), TANPA data dan tanpa menghabiskan token.
5. Hak: untuk aksi baca `Rbac::can(...,'R')`/`Policy::view`; untuk keputusan `Rbac::canDecide($user, modul)` + Policy `putuskan` + investor memiliki `sppg_id` subjek (`SppgAktif::milik`) + `sppg_id` subjek dimuat dari record (bukan dari token) harus sama dengan `sppg_id` token.
6. Konsumsi token atomik (D1), lalu panggil service; service mengulang pemeriksaan pivot dan kunci baris sendiri (pertahanan berlapis).
7. `answerCallbackQuery` + `editMessageText`/`editMessageReplyMarkup` (hapus tombol), log aman `bot.aksi` (jenis, hasil, user_id, subjek, hash chat id) tanpa PII.
- Eksekusi memakai scope SPPG eksplisit: tambah di `App\Support\SppgAktif` metode `untuk(User, int $sppgId, Closure)` yang hanya menerima SPPG yang lolos `milik()` (investor) atau `sppg_id` sendiri (peran lain), menimpa hasil `resolve()` selama closure, dan selalu dibersihkan di `finally`. Tidak ada jalur lain yang membuat `User::sppgAktifId()` non-null di luar HTTP.
- Callback diproses di job `ProcessTelegramUpdate` yang sudah ada (tanpa job baru). Idempotensi update webhook tetap oleh `update_id` unik.

### D6. Alur tanpa sesi penuh (jawab petunjuk login, bukan data)
- `/menu`, `/start` (pengguna terdaftar), `/bantuan`, callback apa pun, dan balasan catatan: bila `! punyaSesiPenuh` -> balasan tetap `TelegramUpdateHandler::PERLU_MASUK` + tombol web_app akar. Tidak ada nama SPPG/menu/angka, tidak ada daftar tombol data. Pesan `/start` setelah onboarding undangan (akun baru tanpa sesi) hanya salam singkat + tombol masuk; ringkasan peran/SPPG yang kini ada di `greet()` dipertahankan hanya untuk pengguna ber-sesi penuh (asumsi A3).
- Pengguna tidak terdaftar / nonaktif: perilaku sekarang dipertahankan (tanpa menu).
- Sesi dicabut di tengah alur (token sudah terbit): langkah 4 D5 menolak; baris `menunggu_catatan` ikut `kedaluwarsa`.

## Asumsi (maks 8; pengguna boleh membatalkan)
- A1. Pintasan layar memakai tombol `web_app` dengan rute di query `?r=` dan hash `#/rute`; tidak memakai tautan `t.me/<bot>/<app>?startapp=`.
- A2. Pemilihan SPPG investor disimpan di baris token (tidak ada preferensi permanen per pengguna), dan investor 1 SPPG melewati pemilih.
- A3. Salam `/start` yang menyebut peran/SPPG hanya untuk pengguna ber-sesi penuh; tanpa sesi: salam netral + petunjuk masuk.
- A4. Bot hanya menyetujui/menolak; `perlu_revisi` pada menu, verifikasi pembelian bahan oleh akuntan, dan pengajuan apa pun tetap di Mini App.
- A5. Notifikasi yang sudah ada (`MenuDiajukan`, `PengeluaranDiajukan`) TIDAK ditambah tombol keputusan; investor masuk lewat `/menu`. (Integrasi tombol "Tinjau" di notifikasi = lanjutan.)
- A6. TTL tombol 10 menit, jendela catatan 10 menit, daftar maksimal 5 butir per jenis.
- A7. Catatan penolakan wajib dikirim sebagai balasan ke pesan `ForceReply`; teks bebas di luar jendela itu tetap ke Agen AI.
- A8. Tidak ada tabel/kolom lama yang diubah; hanya tabel `bot_aksi` baru, dibersihkan terjadwal setelah 30 hari.

## Risiko keamanan (untuk tinjauan opus, read-only)
1. Callback palsu/forwarded: pesan keyboard diteruskan ke orang lain atau pengguna lain menekan tombol di chat grup. Mitigasi: binding `from.id` + `chat.id` + `user_id`; hanya chat pribadi.
2. Replay/tekan ganda dan race: UPDATE atomik sekali-pakai; uji paralel dua update untuk token yang sama (hanya satu memanggil service).
3. Sesi dicabut atau pengguna dinonaktifkan/diganti peran antara render dan tekan: D5 langkah 3-5 dihitung ulang setiap kali; periksa tidak ada cache hak.
4. Investor multi-SPPG: `SppgAktif::untuk` tidak boleh bocor antar job (worker long-running); `sppg_id` token vs record vs pivot harus cocok; IDOR lewat tebakan kode (MAC + TTL + binding).
5. Keputusan basi: versi menu/pengeluaran berasal dari baris token (yang dilihat pengguna), bukan klien; 409 tidak mengubah data. Verifikasi urutan kunci tidak berubah (menu -> pengajuan; sppgs -> pengeluaran -> persetujuan).
6. Catatan penolakan: teks pengguna tidak boleh masuk ke Agen AI, log, atau ringkasan payload; sudah dipotong/escape saat notifikasi `MenuDiputuskan`. Pastikan balasan non-reply tidak salah dianggap catatan dan sebaliknya.
7. Kebocoran data di pesan bot: tinjau layar menampilkan hanya yang sudah ada di notifikasi (tanpa `uraian`, nota, nama penerima, telepon, NIK); semua nilai di-escape HTML.
8. Penyalahgunaan: rate limiter callback, ukuran tabel `bot_aksi` (pembersihan terjadwal, batas token aktif per pengguna, mis. 50), kunci HMAC diturunkan dari `app.key` (rotasi kunci membatalkan token, aman).
9. Deep link: `?r=` harus whitelist/regex (tanpa open redirect, `//`, `..`, skema); hash Telegram pada klien sungguhan belum terverifikasi (dicatat juga di `docs/decisions/2026-10-27-tinjauan-keamanan-r06b2.md`).
10. Pesan tanpa sesi tidak boleh membocorkan keberadaan akun/SPPG; jawaban seragam untuk tombol tidak sah.

## Definition of Done
