## (b) Anggaran memori 2 GiB (t3.small, swap 2 GiB)

Prinsip: batas (`mem_limit`) adalah plafon, bukan alokasi; angka "tipikal" adalah perkiraan awal yang **wajib diukur** (`docker stats`) di staging lalu disetel. Semua batas diparameterkan (`MEM_MYSQL`, `MEM_APP`, ...) agar naik tipe VM saat uji beban tidak perlu mengubah berkas.

| Komponen | Batas | Tipikal | Dasar |
|---|---|---|---|
| OS + dockerd/containerd + sshd (+ agen SSM bila dipakai) | cadangan ~400 MB | 350-400 | Ubuntu 24.04 minimal + Docker. |
| mysql 8.4 | 640m | ~450 | `innodb_buffer_pool_size=256M`, `innodb_redo_log_capacity=128M`, log buffer 16M, `max_connections=40` (4 fpm + 1-2 queue + 2-3 scheduler + backup/migrate, kelonggaran), `performance_schema=OFF` (hemat ~100-200 MB), `skip-name-resolve`, `table_open_cache=400`, `tmp_table_size=max_heap_table_size=32M`, `thread_cache_size=8`, buffer sesi kecil (sort 512K, join 256K), binlog dimatikan (`disable_log_bin`; RPO mengandalkan dump, lihat (e)). `flush_log_at_trx_commit=1` tetap (data keuangan). `memswap_limit` = batas (tanpa swap agar buffer pool tidak di-page-out). |
| app (php-fpm) | 448m | ~220 | `pm=ondemand`, `pm.max_children=4`, `process_idle_timeout=20s`, `pm.max_requests=500`, `request_terminate_timeout=90s`; opcache 64M (naik bila `opcache.max_accelerated_files` perlu); `memory_limit=192M` (GD 30 MP ~120 MB + overhead; 4 x 192M teoretis melebihi batas, ditahan oleh `rate_limit` unggah 20/menit; bila perlu turunkan `unggahan.maks_piksel`). Empat anak karena endpoint AI kemungkinan memblokir hingga puluhan detik (LLM timeout 20 s x `AI_MAX_ITERATIONS`); verifikasi apakah AI sinkron. |
| queue | 192m | ~90 | 1 worker: `queue:work --sleep=3 --tries=3 --max-time=3600 --memory=128 --timeout=80`, `DB_QUEUE_RETRY_AFTER=120` (harus > timeout), `stop_grace_period: 90s`. Worker kedua (replika) hanya bila backlog terukur (+90 MB). |
| scheduler | 160m | ~60 | `schedule:work` memunculkan proses artisan anak sesaat. |
| nginx | 48m | ~10 | Alpine. certbot **tidak residen** (dijalankan sesaat). |
| Jumlah batas | 1488 + OS 400 = ~1890 MB | tipikal ~1,25 GiB | Sisa swap 2 GiB sebagai penyangga; `vm.swappiness=10`; `memswap_limit` kontainer non-MySQL = batas + 256m. Cgroup swap accounting pada kernel AWS Ubuntu 24.04 harus diverifikasi di server. |

Beban sementara: `migrate`/`artisan` sekali jalan (~100 MB, queue+scheduler dihentikan saat itu), backup stream (mysqldump + gzip + age + rclone ~150 MB). Disk 38 GB: rotasi log Docker (`max-size 10m`, `max-file 3`), Laravel `LOG_CHANNEL=daily` 14 hari, `journald` maks 200M, `docker image prune` menyisakan 2 rilis.

Hemat kredit (paket gratis berakhir 2027-03-16; angka harga di bawah perkiraan, belum diverifikasi, cek AWS Pricing Calculator):
- t3.small Singapura sekitar US$19/bulan 24x7, EBS gp3 38 GB sekitar US$3, IPv4 publik/EIP sekitar US$3,7. Total sekitar US$26/bulan 24x7; VM berhenti tetap sekitar US$7 (EBS+EIP).
- Jangan build di server (CPU credit t3 mode unlimited menimbulkan biaya surplus); tanpa ALB/NAT; CloudWatch dasar saja; pasang AWS Budgets/billing alarm (butuh akun pengguna).
- Stop VM saat tak dipakai: webhook Telegram gagal (Telegram mencoba ulang lalu membuang), scheduler terlewat, cadangan terlewat (timer `Persistent=true` mengejar saat nyala). `restart: unless-stopped` + `systemctl enable docker` agar pulih sendiri.
- Uji beban: stop VM, ubah tipe (mis. t3.large), start, uji dari luar (k6 dari laptop), kembalikan. IP statis tetap. Rate limit akan menghambat uji; siapkan akun uji dan pengecualian sementara lewat env, bukan edit kode.

## (c) Desain TLS dan certbot

- Pilihan: certbot **kontainer sesaat** (`certbot/certbot`, profil `tools`) dengan metode **webroot**, bukan certbot di host. Alasan: tanpa paket tambahan, versi terkunci, tanpa soket Docker; nginx dan certbot berbagi volume `certbot_www` (webroot) dan `certbot_etc` (sertifikat, ro di nginx).
- Pembaruan: systemd timer host 2x/hari menjalankan `scripts/renew-cert.sh` = `docker compose run --rm certbot renew --webroot -w /var/www/certbot` lalu `docker compose exec -T nginx nginx -s reload`. Nol proses residen, soket Docker tidak pernah dipasang ke kontainer.
- Bootstrap sertifikat pertama (nginx 443 tidak boleh gagal start tanpa sertifikat): templat nginx dibagi dua: `80.conf.template` (server :80: ACME `/.well-known/acme-challenge/`, `/up`, redirect 301 ke HTTPS) selalu aktif; `443.conf.template` (server :443) disalin oleh skrip `docker/nginx/entrypoint/40-sigap-config.sh` (dipasang ke `/docker-entrypoint.d/`) hanya bila `/etc/letsencrypt/live/$DOMAIN/fullchain.pem` ada. Urutan `scripts/bootstrap-cert.sh`: (1) `up -d nginx` (hanya :80), (2) `certbot certonly --webroot -d $DOMAIN -m $CERTBOT_EMAIL` (opsi `--staging` untuk gladi; batas Let's Encrypt 5 gagal/jam), (3) jalankan ulang `40-sigap-config.sh` lalu `nginx -s reload`. Idempoten.
- DOMAIN via `envsubst` bawaan image nginx (`/etc/nginx/templates/*.template`) dengan `NGINX_ENVSUBST_FILTER=^DOMAIN$` agar `$host`, `$uri` dst. tidak ikut tersubstitusi. Image `web` menyalin templat, bukan `default.conf`.
- Konfigurasi TLS: TLS 1.2/1.3 profil Mozilla intermediate, `ssl_session_cache`, OCSP stapling, HSTS `max-age=15552000` tanpa `preload`/`includeSubDomains` dulu. Hanya 80/443 yang dipublikasikan.
- Domain belum ada: Telegram mewajibkan HTTPS valid untuk webhook dan Mini App, jadi staging butuh nama. Opsi tanpa biaya: `<ip-dengan-strip>.sslip.io` (verifikasi batas Let's Encrypt saat dipakai). Jika domain datang, cukup ubah `DOMAIN`, `APP_URL`, `TELEGRAM_MINIAPP_URL`, jalankan `bootstrap-cert.sh` dan `sigap:telegram-set-webhook`; tidak ada nama yang di-hard-code.

## (d) Desain scripts/deploy.sh

Kontrak: `scripts/deploy.sh [--ref develop|vX.Y.Z] [--set-webhook] [--skip-backup] [--rollback]`. `set -Eeuo pipefail`, kunci `flock`, dijalankan sebagai pengguna `deploy` (anggota grup docker = setara root; catat di (f)). Tidak pernah mencetak nilai `.env`.

Urutan:
1. Preflight: Docker/compose ada; disk bebas >= 5 GB; `.env` ada, mode 600; kunci wajib terisi (DOMAIN, APP_KEY, DB_*, TELEGRAM_*); tolak bila `APP_ENV!=production`, `APP_DEBUG!=false`, `TELEGRAM_DEV_BYPASS` true, secret webhook pendek; `docker compose config -q`; pohon git bersih.
2. `git fetch --tags --prune`; checkout detached ke ref; simpan sha sebelumnya di `.deploy/previous`. `APP_TAG` = tag atau sha7.
3. Dapatkan image: mode `registry` (`docker compose pull`) atau `local` (`docker compose build`, serial, dengan peringatan memori). Gagal di sini = aplikasi lama tetap jalan.
4. `up -d --wait mysql` (sehat). Bila ada migrasi tertunda (`migrate:status --pending`): dump pra-migrasi lokal terkompresi (simpan 3) + unggah via `backup.sh --tag pre-deploy`; gagal dump = batalkan deploy. Migrasi `2026_10_27_000102` tidak idempoten bila gagal di tengah (kolom sudah ada), jadi dump wajib dan jalankan di jam sepi.
5. `artisan down --retry=60` (driver file, volume bersama); hentikan graceful queue dan scheduler.
6. `run --rm --no-deps app php artisan migrate --force`. Gagal setelah titik ini: tetap maintenance, keluar non-nol, cetak instruksi pemulihan (periksa kolom/indeks parsial lalu pulihkan dari dump); sebelum titik ini: otomatis `up`.
7. `up -d --remove-orphans --wait` (urutan app, nginx, queue, scheduler). Cache `config/route/view/event` dibuat saat kontainer mulai lewat `docker/php/entrypoint.sh` (bukan saat build; rahasia hanya ada saat runtime dan `bootstrap/cache` bukan volume).
8. `artisan up`. Health check: `curl -fsS --retry 10 --retry-delay 3 --resolve $DOMAIN:443:127.0.0.1 https://$DOMAIN/up`, semua layanan running/healthy, tidak ada migrasi tertunda; `sigap:telegram-set-webhook --info` (bila `--set-webhook`, jalankan setWebhook idempoten). Tulis `.deploy/history`; `docker image prune` menyisakan rilis saat ini dan sebelumnya.
9. `--rollback`: checkout sha di `.deploy/previous`, `up -d` memakai image lokal bertag lama. **Skema DB tidak diturunkan otomatis** (data berisiko). Kebijakan: migrasi dibuat kompatibel-mundur (expand/contract); bila tidak, pulihkan dump pra-migrasi (kehilangan data sejak itu) dan itu keputusan manusia.

Build di server 2 GiB: tidak memadai sebagai jalur utama. Kompilasi ekstensi PHP (gd, intl) 5-10 menit dengan puncak ~0,6-0,9 GB, ditambah `npm ci`, sementara stack berjalan ~1,25 GiB; risiko swap-thrash/OOM menewaskan MySQL dan membakar CPU credit. **Rekomendasi**: build di GitHub Actions, dorong ke GHCR (tanpa kredensial AWS; verifikasi kuota GHCR sesuai visibilitas repo), `deploy.sh --mode registry` menarik image (~200 MB/rilis). Alternatif ECR di ap-southeast-1: sekitar US$0,1/GB-bulan (< US$0,1/bulan), transfer ke EC2 satu region gratis, tetapi butuh IAM OIDC di akun pengguna. Fallback: build lokal di server saat tak ada lalu lintas. Memerlukan workflow baru milik github-ops (lihat (g)).

## (e) Desain backup

- Isi: `mysqldump --single-transaction --quick --routines --triggers` (dari kontainer mysql) | `gzip` | `age -r <kunci publik>` | `rclone rcat <remote>` (stream, tanpa berkas sementara). Unggahan (`storage/app/secure`, disk `uploads`) di-tar.gz + age mingguan (harian bila < 500 MB). `.env` dan `APP_KEY` TIDAK dicadangkan otomatis: disimpan pemilik di pengelola kata sandi.
- Enkripsi: `age` dengan kunci publik di server; kunci privat dipegang pengguna secara luring. Server yang terbobol tidak bisa membaca arsip lama; konsekuensi: kunci privat hilang = cadangan tak terpulihkan. Data berisi data pribadi (UU PDP): wajib terenkripsi, bucket privat, tanpa akses publik.
- rclone dalam kontainer sesaat; tujuan diganti hanya lewat `BACKUP_REMOTE` dan env rclone (S3/B2/R2/Drive), tanpa mengubah skrip. Skrip tidak bergantung pada pilihan tujuan.
- Retensi: harian 7, mingguan 4, bulanan 3 lewat lifecycle bucket (bukan skrip dengan hak hapus). Jadwal: systemd timer 02:30 WIB, `Persistent=true`, log ke journald; ping pemantau opsional (healthchecks.io, butuh akun).
- RPO: harian + dump pra-deploy (maks ~24 jam). Binlog off. Naikkan ke 6 jam bila diinginkan (biaya hampir nol).
- Skrip: `backup.sh`, `restore.sh <objek>` (secara bawaan memulihkan ke DB sementara `sigap_restore_test`; menimpa produksi butuh `--confirm-overwrite` dan ketikan nama DB), `restore-test.sh`. Uji bertingkat: otomatis tiap cadangan di server (gzip -t, ukuran minimal, penanda "Dump completed", muat ke DB sementara dan bandingkan jumlah baris tabel kunci, lalu drop); uji ujung-ke-ujung (unduh, dekripsi dengan kunci privat, pulihkan) manual dari laptop pengguna sebelum go-live dan tiap bulan, karena server tidak memegang kunci privat.

## (f) Risiko keamanan untuk tinjauan opus (read-only)

1. nginx: CSP (script-src `'self' https://telegram.org`, `frame-ancestors` Telegram untuk `/miniapp/`, `'none'` untuk `/api`; mulai `Report-Only`), HSTS, `nosniff`, `Referrer-Policy`, header tidak hilang akibat pewarisan `add_header`; `server_tokens off`; hanya `= /index.php`; blokir `/.git`, `/storage`, `/vendor`; `default_server` yang menolak Host tak dikenal (444) agar pemindai IP tidak menjangkau aplikasi; `limit_req_zone` per IP untuk `/api/v1/auth*` dan API umum; webhook Telegram dibatasi ke CIDR Telegram (149.154.160.0/20, 91.108.4.0/22; verifikasi daftar resmi) ditambah secret token yang sudah ada; `client_max_body_size 6m` (5 MiB + overhead multipart), PHP `upload_max_filesize=5M`, `post_max_size=6M`; timeout klien pendek (slowloris).
2. Port/jaringan: hanya 80/443 di Compose; mysql tanpa `ports`, jaringan internal terpisah; Docker memintas ufw (iptables), jadi Security Group AWS adalah kontrol utama. IPv6 jangan dipublikasikan (docker-proxy menyamarkan IP klien). Verifikasi IP asli klien terlihat oleh Laravel.
3. Rahasia: hanya lewat `.env` server (mode 600, pemilik `deploy`), bukan `environment:` di compose/git; terlihat di `docker inspect` bagi anggota grup docker; tak ada nilai di `docs/ops/env.production.example`; `TELEGRAM_DEV_BYPASS=false` eksplisit; pembangkitan secret dengan `openssl rand -hex 32`; hindari `$` dan `#` dalam nilai (parsing env_file); log deploy tidak mencetak rahasia.
4. Hardening kontainer: `no-new-privileges`, `cap_drop: ALL` (nginx menambah CHOWN/SETUID/SETGID/NET_BIND_SERVICE), `read_only` + tmpfs bila memungkinkan, non-root untuk php. Tanpa soket Docker di kontainer mana pun.
5. Izin storage: volume `app_storage` milik uid 1000; unggahan di `storage/app/secure` tidak disajikan nginx; `UID/GID` image harus sama dengan pemilik volume.
6. PHP produksi: `display_errors=Off`, `zend.exception_ignore_args=On` (token/NIK tak masuk jejak tumpukan), `expose_php=Off`; log harian dengan retensi 14 hari dan `LOG_LEVEL=warning`.
7. certbot: email, `--staging` untuk gladi, `certbot_etc` hanya-baca di nginx, kunci privat tidak di dalam image atau git.
8. Backup: berisi data pribadi; enkripsi age, hak minimal tanpa Get/Delete pada server, bucket non-publik, kunci privat luring; dump lokal pra-migrasi mode 600 di `/var/backups/sigap` dan dirotasi.
9. Host: SSH hanya kunci, tanpa kata sandi/root, atau cukup SSM Session Manager tanpa port 22; bila SSH, SG dibatasi `<IP-pengguna>/32`; `unattended-upgrades`; fail2ban opsional; IMDSv2 wajib; pengguna `deploy` di grup docker (setara root) dibatasi satu orang.
10. Penyingkapan versi/error: `/up` hanya mengembalikan status; tidak ada halaman debug; `APP_DEBUG=false` dijaga preflight.

## (j) Pertanyaan untuk pengguna (menghalangi)

1. Tujuan backup: S3 ap-southeast-1 dengan instance profile + (opsional) salinan kedua B2/R2? Bawaan: S3 saja dulu, enkripsi age, kunci privat Anda simpan luring. Anda perlu membuat bucket/role dan menyimpan kunci privat; menulis skrip tidak terblokir, go-live terblokir.

3. Jalur image: build di GitHub Actions ke GHCR (bawaan; perlu workflow baru github-ops dan visibilitas repo), dengan build lokal sebagai cadangan?
4. Persetujuan agar backend-dev memiliki sementara Dockerfile, docker/**, scripts/**, docs/ops/**, docker-compose.prod.yml, `.gitattributes` untuk PR ini? Bawaan: ya, dan Anda memperbarui tabel CLAUDE.md/README sesudahnya.
5. RPO dan kebijakan stop VM: cadangan harian + dump pra-deploy (RPO ~24 jam), dan VM tidak dimatikan selama masa uji pengguna (hanya saat idle panjang)? Bawaan: ya.
